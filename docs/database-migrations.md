# Database migrations

The suite stores data in SQLite (standard install) and manages its schema with
**Alembic versioned migrations**. This replaced the older `create_all` startup
call, which could not evolve an existing schema safely.

Nothing here is destructive by default. A migration failure rolls back, and a
pre-migration backup of the SQLite file is written before any pending update is
applied.

## Why

* Existing installations keep their data across upgrades.
* Fresh installations create the schema deterministically.
* A failed update never wipes the database — a backup file is kept.
* The Startup / Setup Wizard can tell the owner, in plain language, whether the
  database is ready, needs an update, or failed.

## Layout

```
alembic.ini                 # locations + logging; the DB URL is resolved at runtime
migrations/
  env.py                    # resolves the URL from app settings; async + batch mode
  script.py.mako            # template for new revisions
  versions/
    <timestamp>_<rev>_baseline_schema.py
backend/app/db/migrate.py   # guarded runner (status / upgrade / current)
docs/database-migrations.md # this document
```

The database URL is **never** stored in `alembic.ini`. `migrations/env.py` calls
`Settings.resolve_database_url()`, so migrations follow the same rules as the app
(`.env`, `DATABASE_URL`, `TCMS_ROOT`, portable layout).

## Day-to-day

Migrations run automatically at application startup (`backend/app/main.py`).
You normally do not need to run anything by hand.

Manual commands (from the repository root, with the virtualenv active):

```bash
python -m backend.app.db.migrate status    # is an update available?
python -m backend.app.db.migrate current   # current revision id
python -m backend.app.db.migrate upgrade    # apply pending updates (with backup)
```

## Creating a new migration

After changing a model:

```bash
alembic revision --autogenerate -m "add channel table"
# review the generated file under migrations/versions/ before committing
python -m backend.app.db.migrate upgrade
```

Always read the autogenerated file. Autogenerate does not detect every change
(table renames, some constraint edits); adjust by hand when needed. Keep the
baseline revision as the initial schema and add new revisions on top — never edit
a revision that has already shipped.

## How each install kind is handled

| Install | Database state | What happens |
|---|---|---|
| Fresh | No file / no tables | Baseline migration creates the full schema |
| Existing (`create_all`) | Tables present, no `alembic_version` | Adopted (stamped at head) — **no table is touched, no data lost** |
| Upgrade | `alembic_version` behind head | Pre-migration backup, then pending revisions applied in a transaction |
| Failure | Any | Rolled back; the backup file name is reported |

## Safety guarantees

* **Existing database is preserved** — an old `create_all` database is stamped,
  not recreated.
* **Existing data is preserved** — adoption performs no DDL.
* **Migration failure does not destroy the database** — each revision runs in a
  transaction (`transaction_per_migration=True`); a raised error rolls back.
* **A backup precedes risky work** — `create_pre_migration_backup()` copies the
  SQLite file to `backups/premigration-<timestamp>-app.db` before applying
  pending revisions. If the copy fails, the upgrade aborts.
* **Startup detects pending migrations** — `database_status()` runs the same
  logic the Setup Wizard uses, so "update available" is visible before the
  owner starts using the app.

## In the user interface

The Setup Wizard shows the database state in plain language (see `docs/UI.md`):

* «База данных готова.»
* «Для базы доступно обновление.» → a button «Обновить базу данных»
* «Идёт обновление структуры базы.»
* «Обновление завершено.»
* «Обновление не удалось. Создан резервный файл.»

Technical details (revision ids, error text) stay in the Error Center / logs.

API endpoints:

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/v1/system/database` | Current migration state (plain language) |
| POST | `/api/v1/system/database/upgrade` | Apply pending updates (backup first) |

## Platform notes

* **Windows portable** — `migrations/` and `alembic.ini` ship next to `app/`; the
  runner resolves them from the installed code, so `TCMS_ROOT` may point at the
  distribution root or at `app/`.
* **Docker/VPS** — `alembic.ini` and `migrations/` are copied into the image;
  the same startup path applies the schema. Volume-mounted `data/` persists the
  database across container restarts.
* **PostgreSQL (future)** — the URL helper is database-agnostic; adding a
  PostgreSQL URL only requires the corresponding driver. SQLite-specific batch
  mode is enabled automatically when the dialect is SQLite.
